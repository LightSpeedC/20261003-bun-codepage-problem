目的

  1. 以前に出した oven-sh/bun#43660 は氷山の一角。「bun 同士のパイプで化ける」は、表に出た症状の 1 つにすぎない
  2. 根本の問題は、bun がコンソールのコードページを変えること。コードページは窓ごとの設定で、同じ窓の全プロセスが共有している
  3. 変えることで、多くの害が出る。害を 1 つずつ実測で示す（「Issue の骨組み」の害の一覧）
  4. だから、コードページを変えないでほしい。コードページを変えた件そのものを問題として、新しい Issue を出す
  5. そうすれば bun#43660 も同時に直る。新しい Issue と bun#43660 の双方に、相互の関連を書き足す

Issue の骨組み

1. 背景

bun#43660 で、cp932 の窓では bun | bun の出力が化け、終了後に 65001 が残ると報告した。これは症状の 1 つだった。

2. 根本の問題

bun は実行中にコンソールの入力・出力コードページを書き換える。コードページは同じ窓の全プロセスで共有されるため、bun の外にまで影響が及ぶ。

3. 害の一覧と証拠

✅ 観測済み ／ ⬜ 未測定。

害証拠状態
H1パイプでつないだ相手の表示が化ける（bun#43660 の症状）。調査の 1.4.2・canary 版、T2・T5✅ 観測済み
H2結果が実行のたびに変わる。起動・終了の順で決まる。調査の 3 回の差、T5✅ 観測済み
H3終了後に 65001 が窓に残る。調査、T1・T5✅ 観測済み
H4同じ窓の別のプロセスが巻き込まれる。cmd が SJIS のスクリプトを読み違え、pause などのメッセージが英語になる。調査、T4✅ 観測済み
H5ほかの bun が窓を 932 に戻した後に、bun が UTF-8 のバイト列をそのまま書いて化ける（WriteConsoleW を使っていない）。調査の 1.4.2 の 3 回目、T5✅ 観測済み
H6強制終了すると元に戻らない。T3✅ 観測済み
H7bun 同士が直接つながっていなくても起きる（bun | node | bun）。T5✅ 観測済み

観測した内容は コードページ試験の結果 と bun#43660 の再現 にある。H2 の原因（起動・終了の順で決まる）は T5 で確かめた。

4. 依頼

コンソールのコードページを変えないでほしい。画面への出力は WriteConsoleW で UTF-16 のまま渡し、パイプ・ファイルにはバイト列をそのまま書けば、コードページに依存しない（「あるべき姿」）。node と deno が変えずに正しく動くことを、実装できる裏付けにする（T1・T2）。

5. bun#43660 も直る

コードページを変えなければ、H1〜H7 はどれも起きない。bun#43660 の症状（H1）もここに含まれる。

前提とあるべき姿

基準の窓

日本語版 Windows で、開いた直後の cmd の窓（コードページ 932）を基準にする。テストはコードページに一切触らない。

IMPORTANT: AIエージェントのセッションの窓は ConPTY 配下で、開始時点で 65001 になっている。そこで直接流すと基準の窓にならない。テストは conhost.exe で新しいコンソールを起こし、その中で走らせる。結果はファイルに書かせて読む。conhost.exe を名指しするのは、既定の端末が Windows Terminal だと新しい窓も ConPTY 配下になりうるため（未検証）。bun#43660 も Windows Terminal ではなく cmd.exe を直接使った条件で報告されている。

テスト項目

期待値

「あるべき姿」の実装なら、全項目で次のとおりになる。

  • node と deno がこの期待値を満たせば、コードページに触らずに実装できることの裏付けになる
  • node や deno が外れた場合は、比べる相手として使えるかを見直す

T1. コードページの推移

基準の窓で、実行前・実行中・終了後の GetConsoleCP ／ GetConsoleOutputCP を記録する。実行中の値は各ランタイム自身が FFI で読む（読むだけ）。bun は bun:ffi、node は koffi、deno は Deno.dlopen。期待値は全時点で 932。

T2. パイプの組み合わせ

軸値
送り手bun / node / deno
受け手bun / node / deno
起動元cmd / pwsh 7 / Windows PowerShell 5.1（いずれも基準の窓の中から起動）

3 × 3 × 3 ＝ 27 通り。受け手は受け取ったバイト列をそのままファイルへ書き、期待する UTF-8 のバイト列と突き合わせる。画面の見た目では判定しない。

NOTE: Windows PowerShell 5.1 は、bun を含まないネイティブコマンド同士のパイプでも非 ASCII が ? になる既知の事象がある。5.1 の行は node | node を基準にし、bun 固有の差だけを見る。

T3. 強制終了後の残留

待機中の bun を taskkill /F で止め、窓が 932 に戻っているかを確かめる。

T4. 同じ窓の隣のプロセスへの影響

bun | bun の直後（通常終了・強制終了）に、SJIS で書いた cmd が日本語を正しく出すかを確かめる。

T5. 順番を固定した再現

2 本以上のプロセスが起動・終了する順番を待ち時間で決め、偶然に頼らずに結果を出す。各プロセスは起動直後・書く直前・終了直前に GetConsoleCP ／ GetConsoleOutputCP を時刻つきでログへ書く（読むだけ）。送る文字列は abc 東京大阪 xyz にする。偶数の文字数（4 文字・12 バイト）で、CP932 として読まれても 2 バイトずつ別の文字に読み替わり、壊れたバイトが残らない。化けると abc 譚ｱ莠ｬ螟ｧ髦ｪ xyz になるため、前後の ASCII と改行は残り、正しい形と化けた形を機械的に見分けられる（node の TextDecoder('shift_jis') による計算。コンソールの表示とは未照合）。

形順番の決め方確かめること
bun | bun起動の順は片側の起動前に ping -n 2 127.0.0.1 >nul、終了の順はスクリプト内の setTimeout起動の順 × 終了の順 × 画面に書く／書かない
bun | node wait | bun間の node が受け取ったデータを決めた時間だけ持ってから流すbun 同士が直接つながっていなくても起きるか（H7）
node | node wait | node同上比べる相手
deno | node wait | deno同上比べる相手
bun#43660 と同じ形順番を決めない（-e で 2 本を同時に起動）。10 回流す結果が回ごとに変わるか（H2）

仮説（各 bun が起動時に今の値を控えて 65001 にし、終了時に控えた値へ戻す）から予想する bun | bun の結果:

起動の順終了の順画面終了後
送り手が先送り手が先化ける65001 が残る
送り手が先受け手が先正しい932 に戻る
受け手が先送り手が先正しい932 に戻る

各組を 3 回ずつ流し、回の順に結果を並べる。経緯は bun#43660 の再現 を参照。

T6. 版の比較

T1〜T5 を bun の安定版と canary 版の両方で流す。node ・ deno は基準として版を 1 つに固定し、記録する。

進め方

  1. deno を導入する（済: 2.9.7）
  2. fixtures とハーネスを作り、T1 で新しいコンソールの仕組みが動くことを確かめる（済）
  3. T1 → T2 → T3 → T4 → T5 の順に 1 項目ずつ足し、そのつど全件を流す（済）
  4. 結果の表を英語版・日本語版の資料にまとめ、害の一覧（H1〜H7）の状態を更新する（済: コードページ試験の結果）
  5. T6 で版を比べる（済: 安定版と canary 版を同じ表に並べた）
  6. 「Issue の骨組み」に沿って本文案を作り、ローカルルール「Issue と公開」の条件を満たしてから出す（本文案は済: 新しい Issue の下書き。投稿は未）
  7. bun#43660 に、新しい Issue への関連を書き足す
