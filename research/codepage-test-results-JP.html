コードページ試験の結果

計画の T1〜T6 を、bun 1.4.2 ・ bun canary ・ node ・ deno で流した結果。bun がコンソールのコードページを変えることで起きる害を、1 つずつ実測で示す

📅 作成: 2026-10-04 / 更新: 2026-10-07

⌂English

要約: bun は起動時にコンソールの入力・出力コードページを控えて両方 65001 にし、終了時に控えた値へ戻す。コードページはコンソールに属し、つながる全プロセスで共有されるため、同時に動く bun 同士が互いの控えを上書きする。その結果、出力が化け、窓に 65001 が残り、同じ窓のほかのプログラムが壊れる。node と deno はコードページを一度も変えず、すべてのケースで正しかった。英語版 Windows のコードページ 437 でも再現する。詳しくは 結論。

判定の方法

  • コードページ: 各プロセスが起動直後・書く直前・終了直前に GetConsoleCP ／ GetConsoleOutputCP を読み、時刻と一緒に記録する。窓の前後は観測役の node が読む（T1 で node がコードページを変えないことを確かめている）
  • 画面: 観測役が ReadConsoleOutputCharacterW で窓の文字を読み取る。人の目には頼らない
  • 隣のプロセス: 各ケースの最後に、同じ窓で chcp と、SJIS で書いた cmd（echo sjis: 東京大阪）を流し、画面に残った表示を見る
  • バイト列: 受け手が受け取ったバイト列をそのままファイルに書き、正しい UTF-8 かを見る

✅ 期待どおり（あるべき姿と同じ） ／ ❌ 期待と違う。同じ組を何回か流したものは、回の順に並べる。

  • 各ケースの最後に流す共通の後始末（new-console.ts の 94〜100 行）。chcp、SJIS の cmd、観測役による画面の読み取り

結論

bun は、起動した瞬間（スクリプトが動く前）に窓の入力・出力コードページを 65001 に変え、終了時に「起動時に控えた値」へ戻す。この動きから、計画の害 H1〜H7 がすべて起きることを確かめた。node と deno はコードページを一度も変えず、すべてのケースで正しく動いた。

パイプを流れるデータそのものは、どの組み合わせでも壊れなかった（T2）。害はすべて、窓のコードページという共有の状態を書き換えることから起きている。安定版と canary 版の結果は、すべてのケースで同じだった（T6）。

bun のソースの該当箇所

  • init()（output.rs の 561〜567 行）が GetConsoleOutputCP ／ GetConsoleCP の値を控え、SetConsoleOutputCP(65001) ／ SetConsoleCP(65001) を呼ぶ
  • restore()（output.rs の 517〜524 行）が終了時に控えた値へ戻す
  • ソースのコメント にも「強制終了されると戻らないことがある」とある（H6）

リンクはいまの main を指す。T5 の時系列は、このコードとそのまま一致する。各プロセスは起動時に見えた値を控えるので、2 本目は 65001 を控える。

Issue に載せる順番を決めた再現を、コードページ 437（英語版 Windows の既定）で始めた窓でも、このスクリプトで各版 3 回ずつ流した。bun 1.4.2 と canary は毎回 abc µ¥▒Σ║¼σñºΘÿ¬ xyz と出し、Active code page: 65001 を残した。node と deno（deno eval）は毎回 abc 東京大阪 xyz と出し、437 のままだった。932 で始めた窓でも同じ形になり、bun は化けて 65001 を残し、node と deno は正しく出して 932 のままだった。上の試験は日本語版の既定の 932 で流している。
