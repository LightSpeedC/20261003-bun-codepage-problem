## 1. 要点

1. <strong>bun は起動時にコンソールのコードページを 65001 に切り替え、終了時に控えた値へ戻す。</strong>コードページはコンソールに属し、つながる全プロセスで共有される。ソース: `init()`（[output.rs の 561〜567 行](https://github.com/oven-sh/bun/blob/3f1765a6de030d00a98c33ff0c776c7a7e4b23e9/src/bun_core/output.rs#L561-L567)）と `restore()`（[output.rs の 517〜524 行](https://github.com/oven-sh/bun/blob/3f1765a6de030d00a98c33ff0c776c7a7e4b23e9/src/bun_core/output.rs#L517-L524)）。証拠、bun が動いているあいだのコードページ: [932](evidence/cp932/bun/node-test/t1-bun/log.jsonl) ／ [437](evidence/cp437/bun/node-test/t1-bun/log.jsonl)（T1）
2. <strong>1 つの窓で 2 本の bun が動くと、互いの控えを上書きする。</strong>出力が化け、窓に 65001 が残り、同じ窓のほかのプログラムが壊れる。証拠: 化けた画面 [932](evidence/cp932/bun/node-test/t5-bun-ww-console-1/screen.json) ／ [437](evidence/cp437/bun/node-test/t5-bun-ww-console-1/screen.json)（T5）、壊れた隣のプロセス [932](evidence/cp932/bun/node-test/t4-bun/screen.json) ／ [437](evidence/cp437/bun/node-test/t4-bun/screen.json)（T4）、強制終了 [932](evidence/cp932/bun/node-test/t3-bun/log.jsonl) ／ [437](evidence/cp437/bun/node-test/t3-bun/log.jsonl)（T3）
3. **bun#43660 への Open の修正 PR #43662 は、原因を取り除かない。**`console.log` の出力は直すが、動いているあいだは窓を 65001 にしたまま（[932](evidence/cp932/bun-pr-43662/node-test/t1-bun/log.jsonl) ／ [437](evidence/cp437/bun-pr-43662/node-test/t1-bun/log.jsonl)）、強制終了では 65001 が残り（[932](evidence/cp932/bun-pr-43662/node-test/t3-bun/screen.json) ／ [437](evidence/cp437/bun-pr-43662/node-test/t3-bun/screen.json)）、`fs.writeSync(1)` ・ `fs.write(1)` ・ `Bun.write(Bun.stdout)` は化け（[932](evidence/cp932/bun-pr-43662/node-test/t5-bun-ww-fswritesync-1/screen.json) ／ [437](evidence/cp437/bun-pr-43662/node-test/t5-bun-ww-fswritesync-1/screen.json)）、戻し方は、順番を決めない形でまれに競合に負ける（[時系列](#窓の全プロセスの時系列pr-43662)）

### PR #43662（bun#43660 への、Open の修正）

[PR #43662](https://github.com/oven-sh/bun/pull/43662) は、`bun_sys::write` を通る画面への出力を `WriteConsoleW` にし、終了時は控えた値が 65001 でないときだけ戻す。CI の Windows x64 のビルドを、同じ試験一式で流した。bun#43660 で報告した症状は直るが、起動時に 65001 にすることは残るため、共有の状態を変えることから起きる害は残る。

- bun が動いているあいだ、窓につながる全プロセスにとってコードページは 65001（T1）
- 強制終了すると 65001 が残り、そのあと同じ窓で動くスクリプトは読み違える（T3）
- `fs.writeSync(1)` ・ `fs.write(1)` ・ `Bun.write(Bun.stdout)` は `WriteFile` のままなので、ww の順では化ける（T5）。PR の説明文とレビューにも、そう書かれている
- 「自分が変えたコードページだけを戻す」でも、競合に負けることがある。2 本とも終わったあと、入力側か出力側の片方だけが 65001 のまま残る。起きる頻度は回ごとに大きく変わり、120 回で 0 回のときも、60 回で 3 回のときもあった。[時系列](#窓の全プロセスの時系列pr-43662)を参照。PR のソースから順番も導いている
- 2026-10-16（JST）に PR へ入ったコミット [6b5271c](https://github.com/oven-sh/bun/pull/43662/commits/6b5271c) は、起動時に窓がすでに 65001 なら `SetConsoleOutputCP` と `SetConsoleCP` を呼ばない。437 や 932 の窓は、これまでどおり 65001 に書き換える。この資料の結果はこのコミットより前の版で測ったもので、このコミットでは bun#44693 の求める実装にならない。このコミットを含む版（先頭コミット 6b5271cb1）で、932 と 437 の全件を流し直したところ、PR の版の判定は 576eb251a のときと 1 件も違わなかった。順番を決めない回（asis）は 932 と 437 で 60 回ずつ、すべて正しく出て、コードページも戻った。強制終了で 65001 が残ることなど、PR のあとも残る害も変わらない

パイプを流れるデータそのものは、どの組み合わせでも壊れなかった（T2）。害はすべて、窓のコードページという共有の状態を書き換えることから起きている。順番を決めたケースは、安定版と canary 版ですべて同じ判定になり（T6）、932 と 437 でもすべて同じだった。

### 関連する PR

[PR #43662 での robobun の返信](https://github.com/oven-sh/bun/pull/43662#issuecomment-6096243719)に出てきたもの。2026-10-10 の時点で、どちらも open で、マージされていない。

- [PR #38140](https://github.com/oven-sh/bun/pull/38140)（robobun、「メンテナーの確認待ち」）: コンソールの標準入力を、`ReadFile` ではなく `ReadConsoleW` で読む。いまは REPL ・ `prompt()` ・ `alert()` ・ `confirm()` ・ `bun init` ・ `bun update -i` ・ `bun -` が `ReadFile` で読み、入力側のコードページで変換される。Windows 10 / Server 2019 の conhost では、65001 での変換が ASCII 以外の入力を壊す。`process.stdin` ・ `Bun.stdin` ・ `fs.readSync(0)` は libuv を通るため影響を受けない。robobun によれば、起動時に 65001 にするのをやめるには、入力側がいまそれに頼っているため、この PR が先に要る。PR 自身は「壊れているのは ANSI 版の変換で、コードページではない」と書いている
- [PR #42819](https://github.com/oven-sh/bun/pull/42819)（dylan-conway）: Windows で libuv を外し、I/O 完了ポートの独自のイベントループにする。パイプ ・ コンソール ・ ファイルは `src/io/windows/` に移る。robobun によれば、これのあと `fs.writeSync` ・ `fs.write` ・ `Bun.write` の書き込みの手当ては `src/sys/windows/fs.rs::write_at` 1 か所で済む。直る不具合の一覧に「別のプロセスがコードページを戻した後、`process.stdout.write` が化けていた（`console.log` はまだ化ける）」があり、ここで測った害と合う

### 化ける順番での時系列（bun 1.4.3、ww ・ 画面、932）

[このログ](evidence/cp932/bun/node-test/t5-bun-ww-console-1/log.jsonl) から。値は 入力/出力。w は送り手、r は受け手、probe は観測役の node。437 で流した回も、932 が 437 に替わるだけで同じ形になる（[ログ](evidence/cp437/bun/node-test/t5-bun-ww-console-1/log.jsonl)）。

```text
   0ms probe  窓の前          932/932
  45ms w      起動直後        65001/65001   ← 送り手が 932 を控えて 65001 にする
  47ms w      書く直前        65001/65001
1093ms r      起動直後        65001/65001   ← 受け手は 65001 を「元の値」として控える
2050ms w      終了直前        65001/65001   → 送り手が終了し、控えた 932 に戻す
2854ms r      書く直前        932/932       ← 受け手は 932 の窓に UTF-8 のバイト列を書く（化ける）
2860ms r      終了直前        932/932       → 受け手が終了し、控えた 65001 に戻す
2989ms probe  窓の後          65001/65001   ← 65001 が残る
```

#### PR のソースから導いた順番

試した版は PR の先頭コミット `576eb251a`。コードページを変えるのは、その `output.rs` だけ:

- `init()`（[output.rs の 581〜585 行](https://github.com/oven-sh/bun/blob/576eb251af6a8e7deb961d17cf839ad393c5cf73/src/bun_core/output.rs#L581-L585)）は、別々の 4 つの呼び出しで動く。出力側を控える、出力側を 65001 にする、入力側を控える、入力側を 65001 にする
- `restore()`（[output.rs の 536〜544 行](https://github.com/oven-sh/bun/blob/576eb251af6a8e7deb961d17cf839ad393c5cf73/src/bun_core/output.rs#L536-L544)）は、出力側、入力側の順に控えた値へ戻す。ただし控えた値が 65001 の側は戻さない

呼ぶのが W と R だけなら、どの終わり方にも、それを生む順番は 1 つしかない:

- **入力側が 65001 で残る（45・51 回目）:** 最後の入力側の変更が、誰も戻さない 65001 への変更でなければならない。W は 932 を控えたので、W の後始末は入力側を 932 にする。その後に来られるのは R の「入力側を 65001 にする」だけで、R が戻さないのだから R は 65001 を控えている。順番は、R が入力側を控える（65001）→ W が終わって入力側を 932 に戻す → R が入力側を 65001 にする。W の後始末が、R の「控える」と「変える」の間に入った
- **出力側が 65001 で残る（19 回目）:** 出力側で同じ順番が起きた。R が出力側を控える（65001）→ W が出力側を 932 に戻す → R が 65001 にする。入力側が戻ったのは、R が入力側を控えたのが W の後始末の後（932）で、R の後始末が .263 に戻したため
- どの回も原因は同じ。R の「控える」と「変える」が 1 つの操作になっておらず、その間に W の後始末が入る。すると R は 65001 を「元の値」として控え、PR の判定は 65001 を控えた側を戻さない

ここまではソースと時刻からの推論。見張り役にはどのプロセスが呼んだかは見えず、R の「控える」と「変える」の間は読み取りの間隔より短い（19 回目で、出力側が 932 になってまた 65001 に戻った変化は記録に出ていない）。そこで次に、呼び出しを 1 つずつ記録した。

### 判定の方法

- **コードページ:** 各プロセスが起動直後・書く直前・終了直前に `GetConsoleCP` ／ `GetConsoleOutputCP` を読む。窓の前後は観測役の node が読む（T1 で node がコードページを変えないことを確かめている）
- **画面:** 観測役が `ReadConsoleOutputCharacterW` で窓の文字を読み取る。人の目には頼らない
- **隣のプロセス:** 各ケースの最後に、同じ窓で `chcp` と隣のプロセス役の cmd を流す。cmd は開始のコードページで書いてある（932 用は SJIS の `neighbor: 東京大阪`、437 用は CP437 の `neighbor: café`）
- **バイト列:** 受け手が受け取ったバイト列をそのままファイルに書き、正しい UTF-8 かを見る

✅ 期待どおり（あるべき姿と同じ） ／ ❌ 期待と違う。**下の表の ✅ と ❌ は、1 つ 1 つがそのケースの証拠ファイルへのリンク**になっている。画面（`screen.json`）、コードページの記録（`log.jsonl`）、受け取ったバイト列（`out.bin`）のどれか。
