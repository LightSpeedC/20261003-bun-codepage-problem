# コードページ試験の結果

計画の T1〜T6 を、bun 1.4.2 ・ bun canary ・ node ・ deno で流した結果。bun がコンソールのコードページを変えることで起きる害を、1 つずつ実測で示す

> 📅 作成: 2026-10-04 / 更新: 2026-10-06

[⌂](../README-JP.md)

[English](codepage-test-results.md)

**要約:** bun は起動時にコンソールの入力・出力コードページを控えて両方 65001 にし、終了時に控えた値へ戻す。コードページはコンソールに属し、つながる全プロセスで共有されるため、同時に動く bun 同士が互いの控えを上書きする。その結果、出力が化け、窓に 65001 が残り、同じ窓のほかのプログラムが壊れる。node と deno はコードページを一度も変えず、すべてのケースで正しかった。英語版 Windows のコードページ 437 でも再現する。詳しくは [結論](#2-結論)。

## 1. 条件

| 項目 | 値 |
|---|---|
| OS | Windows 11 Home 10.0.26300（日本語版） |
| 窓 | ケースごとに `conhost.exe` で新しい窓を起こす。開始時は 932。テストはコードページに触らない |
| bun | 1.4.2+744846f84 |
| bun canary | 1.4.3-canary.1+bb35d1b81 |
| node | v26.10.0 |
| deno | 2.9.7 |
| 送る文字列 | `abc 東京大阪 xyz`（化けると `abc 譚ｱ莠ｬ螟ｧ髦ｪ xyz`） |
| テスト | `tests/codepage.test.ts`。`tools/40_test/run-tests.cmd` で node --test と bun test の両方で流す |

### 判定の方法

- **コードページ:** 各プロセスが起動直後・書く直前・終了直前に `GetConsoleCP` ／ `GetConsoleOutputCP` を読み、時刻と一緒に記録する。窓の前後は観測役の node が読む（T1 で node がコードページを変えないことを確かめている）
- **画面:** 観測役が `ReadConsoleOutputCharacterW` で窓の文字を読み取る。人の目には頼らない
- **隣のプロセス:** 各ケースの最後に、同じ窓で `chcp` と、SJIS で書いた cmd（`echo sjis: 東京大阪`）を流し、画面に残った表示を見る
- **バイト列:** 受け手が受け取ったバイト列をそのままファイルに書き、正しい UTF-8 かを見る

✅ 期待どおり（あるべき姿と同じ） ／ ❌ 期待と違う。同じ組を何回か流したものは、回の順に並べる。

## 2. 結論

bun は、起動した瞬間（スクリプトが動く前）に窓の入力・出力コードページを 65001 に変え、終了時に「起動時に控えた値」へ戻す。この動きから、計画の害 H1〜H7 がすべて起きることを確かめた。node と deno はコードページを一度も変えず、すべてのケースで正しく動いた。

| 害 | 内容 | bun ・ canary | node ・ deno | 証拠 |
|---|---|---|---|---|
| H1 | パイプでつないだ相手の表示が化ける | ❌ 起きた | ✅ 起きない | T5 の ww ・ relay、T4 |
| H2 | 結果が起動・終了の順で決まり、実行のたびに変わる | ❌ 起きた | ✅ 起きない | T5 の 4 通りで結果が分かれる。bun#43660 と同じ形 |
| H3 | 終了後に 65001 が窓に残る | ❌ 起きた | ✅ 起きない | T2（cmd）、T5 の ww ・ rr ・ relay |
| H4 | 同じ窓の別のプロセスが巻き込まれる | ❌ 起きた | ✅ 起きない | T3 ・ T4、T5（SJIS の cmd が化け、chcp のメッセージが英語になる） |
| H5 | コードページが 932 に戻った状態で、bun が UTF-8 のバイト列を書いて化ける | ❌ 起きた | ✅ 起きない | T5 の ww: 受け手が書く直前のコードページが 932 |
| H6 | 強制終了すると元に戻らない | ❌ 起きた | ✅ 起きない | T3 |
| H7 | bun 同士が直接つながっていなくても起きる | ❌ 起きた | ✅ 起きない | T5 の relay（`bun \| node \| bun`） |

パイプを流れるデータそのものは、どの組み合わせでも壊れなかった（T2）。害はすべて、窓のコードページという共有の状態を書き換えることから起きている。安定版と canary 版の結果は、すべてのケースで同じだった（T6）。

### bun のソースの該当箇所

- `init()`（[output.rs の 561〜567 行](https://github.com/oven-sh/bun/blob/3f1765a6de030d00a98c33ff0c776c7a7e4b23e9/src/bun_core/output.rs#L561-L567)）が `GetConsoleOutputCP` ／ `GetConsoleCP` の値を控え、`SetConsoleOutputCP(65001)` ／ `SetConsoleCP(65001)` を呼ぶ
- `restore()`（[output.rs の 517〜524 行](https://github.com/oven-sh/bun/blob/3f1765a6de030d00a98c33ff0c776c7a7e4b23e9/src/bun_core/output.rs#L517-L524)）が終了時に控えた値へ戻す
- [ソースのコメント](https://github.com/oven-sh/bun/blob/3f1765a6de030d00a98c33ff0c776c7a7e4b23e9/src/bun_core/output.rs#L482-L484) にも「強制終了されると戻らないことがある」とある（H6）

リンクはいまの `main` を指す。T5 の時系列は、このコードとそのまま一致する。各プロセスは起動時に見えた値を控えるので、2 本目は 65001 を控える。

### コードページ 437 でも再現する

Issue に載せる順番を決めた再現を、コードページ 437（英語版 Windows の既定）で始めた窓でも、各版 3 回ずつ流した。bun 1.4.2 と canary は毎回 `abc µ¥▒Σ║¼σñºΘÿ¬ xyz` と出し、`Active code page: 65001` を残した。node は `abc 東京大阪 xyz` と出し、437 のままだった。上の試験は日本語版の既定の 932 で流している。

## 3. T1. コードページの推移

1 本だけを窓で動かし、画面に `abc 東京大阪 xyz` を出す。値は 入力/出力。

| ランタイム | 起動直後 | 書く直前 | 終了直前 | 終了後 | 画面 |
|---|---|---|---|---|---|
| bun 1.4.2 | ❌ 65001/65001 | ❌ 65001/65001 | ❌ 65001/65001 | ✅ 932/932 | ✅ |
| bun canary | ❌ 65001/65001 | ❌ 65001/65001 | ❌ 65001/65001 | ✅ 932/932 | ✅ |
| node | ✅ 932/932 | ✅ 932/932 | ✅ 932/932 | ✅ 932/932 | ✅ |
| deno | ✅ 932/932 | ✅ 932/932 | ✅ 932/932 | ✅ 932/932 | ✅ |

- bun は、スクリプトの最初の行が動く時点で、すでに 65001 にしている。画面に何も書かなくても変える
- node と deno は 932 のまま、日本語を画面に正しく出した。コードページを変えなくても正しく表示できることの裏付けになる
- 1 本だけなら、bun も終了時に 932 へ戻すので、問題は表に出ない

## 4. T2. パイプの組み合わせ

送り手と受け手を同時に起動し、受け手は受け取ったバイト列をファイルに書く。各セルは「バイト列 ／ 終了後のコードページ」。

| 送り手 → 受け手 | cmd から | pwsh 7 から | Windows PowerShell 5.1 から |
|---|---|---|---|
| bun → bun | ✅ ／ ❌ 65001 | ✅ ／ ❌ 65001 | ✅ ／ ✅ 932 |
| bun → canary、canary → bun、canary → canary | ✅ ／ ❌ 65001 | ✅ ／ ❌ 65001 | ✅ ／ ✅ 932 |
| bun ・ canary → node ・ deno | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 |
| node ・ deno → bun ・ canary | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 |
| node ・ deno → node ・ deno | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 | ✅ ／ ✅ 932 |

- パイプを流れるバイト列は、どの組み合わせでも壊れなかった
- bun 同士を cmd ・ pwsh 7 から直接つなぐと、終了後に 65001 が残った（H3）。片方が node か deno なら残らない。bun#43660 の「片方が node なら起きない」と合う
- Windows PowerShell 5.1 は、どの組み合わせでも日本語を `?` に置き換える（node | node でも同じ。5.1 自身の事象）。5.1 の列は node | node と同じバイト列なら ✅ とした。5.1 が間に入ると 2 本の bun の寿命がずれるためか、65001 は残らなかった（原因は未確認）

## 5. T3・T4. 強制終了と隣のプロセス

### T3. 強制終了

画面に書いたあと待機している 1 本を `taskkill /F` で止める。

| ランタイム | 終了後のコードページ | chcp の表示 | SJIS の cmd |
|---|---|---|---|
| bun ・ canary | ❌ 65001/65001 | ❌ `Active code page: 65001` | ❌ `sjis: �������` |
| node ・ deno | ✅ 932/932 | ✅ `現在のコード ページ: 932` | ✅ `sjis: 東京大阪` |

bun は終了時に戻す作りのため、強制終了されると 65001 のまま残る（H6）。そのあと同じ窓で動く cmd は、SJIS で書いた自分のスクリプトを 65001 で読み違えて化ける（H4）。

### T4. 通常終了の後

`bun | bun` が普通に終わった後（2 本の寿命が重なり、送り手が先に終わる順）の窓の画面。

```text
abc 譚ｱ莠ｬ螟ｧ髦ｪ xyz
--- tail ---
Active code page: 65001
sjis: �������
```

node ・ deno で同じことをした窓の画面:

```text
abc 東京大阪 xyz
--- tail ---
現在のコード ページ: 932
sjis: 東京大阪
```

bun ・ canary とも、強制終了しなくても同じ窓の cmd と `chcp` のメッセージまで巻き込んだ（H4）。

## 6. T5. 順番を固定した再現

2 本目の起動を約 1 秒遅らせ、終了の順は待ち時間で決める。2 本の寿命は必ず重なるようにした。各組 3 回。セルは「画面またはバイト列 ／ 終了後に 932」。

| 形と順番 | 受け手の書き先 | 仮説の予想 | bun 1.4.2 | bun canary | node ・ deno |
|---|---|---|---|---|---|
| 送り手が先に起動し、先に終わる（ww） | 画面 | 化ける ／ 65001 が残る | ❌❌❌ ／ ❌❌❌ | ❌❌❌ ／ ❌❌❌ | ✅✅✅ ／ ✅✅✅ |
| 同上 | ファイル | 65001 が残る | ✅✅✅ ／ ❌❌❌ | ✅✅✅ ／ ❌❌❌ | ✅✅✅ ／ ✅✅✅ |
| 送り手が先に起動し、受け手が先に終わる（wr） | 画面 ・ ファイル | 正しい ／ 932 に戻る | ✅✅✅ ／ ✅✅✅ | ✅✅✅ ／ ✅✅✅ | ✅✅✅ ／ ✅✅✅ |
| 受け手が先に起動し、送り手が先に終わる（rw） | 画面 ・ ファイル | 正しい ／ 932 に戻る | ✅✅✅ ／ ✅✅✅ | ✅✅✅ ／ ✅✅✅ | ✅✅✅ ／ ✅✅✅ |
| 受け手が先に起動し、受け手が先に終わる（rr） | 画面 ・ ファイル | 正しい ／ 65001 が残る | ✅✅✅ ／ ❌❌❌ | ✅✅✅ ／ ❌❌❌ | ✅✅✅ ／ ✅✅✅ |
| 間に node を挟み、送り手が先に起動して先に終わる（relay） | 画面 | 化ける ／ 65001 が残る | ❌❌❌ ／ ❌❌❌ | ❌❌❌ ／ ❌❌❌ | ✅✅✅ ／ ✅✅✅ |

bun ・ canary の結果は、すべての組で仮説の予想と一致し、3 回とも同じだった。順番さえ決まれば結果は決まる。

### 化ける順番での時系列（bun 1.4.2、ww ・ 画面）

値は 入力/出力。w は送り手、r は受け手、probe は観測役の node。

```text
   0ms probe  窓の前          932/932
  54ms w      起動直後        65001/65001   ← 送り手が 932 を控えて 65001 にする
  59ms w      書く直前        65001/65001
1115ms r      起動直後        65001/65001   ← 受け手は 65001 を「元の値」として控える
2061ms w      終了直前        65001/65001   → 送り手が終了し、控えた 932 に戻す
2867ms r      書く直前        932/932       ← 受け手は 932 の窓に UTF-8 のバイト列を書く（化ける）
2896ms r      終了直前        932/932       → 受け手が終了し、控えた 65001 に戻す
3076ms probe  窓の後          65001/65001   ← 65001 が残る
```

- 受け手の bun は、窓が 932 のときに UTF-8 のバイト列をそのまま書いた。画面に出す文字を `WriteConsoleW` で渡していれば、コードページに関係なく正しく出たはずである（node ・ deno は 932 のまま正しく出している）
- relay では、間の node は何も変えていない。それでも 2 本の bun の寿命が重なるだけで同じことが起きた（H7）

## 7. T5. bun#43660 と同じ形

bun#43660 と同じ形で、2 本を同時に起動し、順番を決めずに 10 回流した。文字列は `\u` エスケープで渡した `abc 東京大阪 xyz`。

```batch
bun -e "console.log('abc 東京大阪 xyz')" | bun -e "process.stdin.pipe(process.stdout)"
```

| ランタイム | 画面（回の順） | 終了後に 932（回の順） |
|---|---|---|
| bun 1.4.2 | ❌✅✅❌❌❌❌❌❌❌ | ❌✅✅❌❌❌❌❌❌❌ |
| bun canary | ✅✅✅❌✅✅❌✅❌❌ | ✅✅✅❌✅✅❌❌❌❌ |
| node | ✅✅✅✅✅✅✅✅✅✅ | ✅✅✅✅✅✅✅✅✅✅ |
| deno | ✅✅✅✅✅✅✅✅✅✅ | ✅✅✅✅✅✅✅✅✅✅ |

- 同じコマンドでも、bun は回ごとに結果が変わった（H2）。2 本のどちらが先に起動・終了するかで決まり、その順は OS の都合で毎回揺れる
- canary 版の 8 回目は、画面は正しいのに 65001 が残った。T5 の rr と同じ順になった回とみられる
- bun#43660 で「化ける」と報告した現象は、この揺れのうち化ける側を見たものだった
